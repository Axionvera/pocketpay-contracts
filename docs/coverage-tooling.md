# Coverage Tooling Research Note

> **Status:** Research document — no tooling has been added to the project as a
> result of this note.
>
> **Review date:** 2026-07-28
> **Scope:** `contracts/savings_vault`

## Summary

This note surveys Rust code coverage tools and evaluates their suitability for
the Savings Vault Soroban contract. The key finding is that **source-based LLVM
coverage (`cargo-llvm-cov`) is the recommended approach**, but Soroban's
`wasm32-unknown-unknown` target introduces significant setup complexity and
experimental caveats. Native (host) target coverage is straightforward and can
be added to CI with minimal effort.

## 1. Candidate Tools

| Tool | Approach | Platforms | Wasm Support |
| --- | --- | --- | --- |
| `cargo-llvm-cov` | LLVM source-based (`-C instrument-coverage`) | Linux, macOS, Windows | Experimental (requires nightly + `wasm-bindgen` workflow) |
| `cargo-tarpaulin` | ptrace-based binary instrumentation | Linux x86-64 only | Experimental via wasm-bindgen guide |
| `grcov` | Post-processing of LLVM `.profraw` files | Any (processes coverage data) | Same underlying pipeline as `cargo-llvm-cov` |

### 1.1 `cargo-llvm-cov` (Recommended)

[cargo-llvm-cov](https://github.com/taiki-e/cargo-llvm-cov) wraps LLVM's
source-based coverage instrumentation. It is the modern, actively maintained
choice for Rust coverage and is officially recommended by both the Rust project
and the Stellar documentation.

**Advantages:**

- Line, region, and (on nightly) branch coverage.
- Fast — only instruments necessary crates.
- Works on all major platforms.
- Integrates with CI services (Codecov, Coveralls) via LCOV output.
- Active development, frequent releases, large community.

**Installation:**

```bash
cargo install cargo-llvm-cov
```

**Basic usage (host target):**

```bash
cargo llvm-cov test
cargo llvm-cov test --html --open
cargo llvm-cov test --lcov --output-path lcov.info
```

### 1.2 `cargo-tarpaulin` (Not recommended for this project)

[cargo-tarpaulin](https://github.com/xd009642/tarpaulin) is an older tool that
uses ptrace to instrument binaries at runtime. It is Linux x86-64-only, which
immediately makes it unsuitable for macOS-based development workflows.

**Limitations:**

- Linux-only (no macOS or Windows support).
- Wasm support is experimental and requires the same nightly workflow as
  `cargo-llvm-cov`.
- Slower than `cargo-llvm-cov` on large workspaces.
- Less actively maintained upstream (wasm support issue has been open since
  2022).

### 1.3 `grcov` (Alternative for advanced pipelines)

[grcov](https://github.com/mozilla/grcov) processes raw `.profraw` files
generated by LLVM instrumentation. It is useful when you need fine-grained
control over the coverage pipeline (e.g., merging results from multiple test
runs, handling C/C++ FFI coverage). For most use cases, `cargo-llvm-cov`
provides a simpler interface that wraps grcov's functionality.

## 2. Soroban-Specific Limitations

Soroban contracts compile to `wasm32-unknown-unknown`. Coverage tooling for
Wasm targets is **experimental** and requires several workarounds:

### 2.1 LLVM cannot read debug info from `.wasm`

LLVM's `llvm-cov` tool cannot directly map profile data to source code from a
`.wasm` binary. The workaround is:

1. Compile with `--emit=llvm-ir` to produce LLVM IR (`.ll`) files.
2. Use `clang` to compile the `.ll` files into native object files (`.o`).
3. Pass those `.o` files to `llvm-cov` for report generation.

This adds compilation time and requires matching LLVM/Clang versions.

### 2.2 Requires Rust Nightly

The Wasm coverage workflow requires Rust Nightly for the
`-Zno-profiler-runtime` flag and the `minicov` profiling runtime:

```bash
RUSTFLAGS="-Cinstrument-coverage -Zno-profiler-runtime --emit=llvm-ir" \
CFLAGS_wasm32_unknown_unknown="-matomics -mbulk-memory" \
cargo +nightly llvm-cov test --target wasm32-unknown-unknown
```

### 2.3 Test runner compatibility

Coverage collection requires `wasm-bindgen-test-runner` (or the Soroban test
runner equivalent). Standard `cargo test` against the host target works
natively, but tests that specifically exercise Wasm execution paths require the
experimental Wasm coverage pipeline.

### 2.4 This project's test structure

The Savings Vault tests (`contracts/savings_vault/src/test/`) run natively
against the host target using `soroban_sdk`'s test utilities — they do **not**
require Wasm execution. This means:

- **Host-target coverage works today.** `cargo llvm-cov test` from the
  workspace root produces meaningful coverage data for test code.
- **Wasm-target coverage is not needed for current test coverage.** Only
  become relevant if tests require Wasm execution (e.g., integration tests
  against a deployed testnet contract).

## 3. CI Impact

### 3.1 Adding host-target coverage to CI

Adding `cargo-llvm-cov` to the existing CI workflow is low-effort:

```yaml
- name: Install cargo-llvm-cov
  uses: taiki-e/install-action@v2
  with:
    tool: cargo-llvm-cov

- name: Generate coverage
  run: cargo llvm-cov --lcov --output-path lcov.info

- name: Upload to Codecov
  uses: codecov/codecov-action@v4
  with:
    files: lcov.info
```

**Estimated CI time increase:** 60-90 seconds per run (coverage compilation is
slower than plain `cargo test`).

### 3.2 Adding Wasm-target coverage to CI

Adding Wasm coverage would require:

- Rust Nightly toolchain installation.
- `wasm-bindgen-test-runner` and `clang` installation.
- `CFLAGS` environment configuration.
- 2-3 minutes additional CI time.
- Acceptance of experimental, potentially brittle coverage output.

**Verdict:** Not recommended for CI integration until Wasm coverage matures
upstream.

## 4. Recommendation

**Add `cargo-llvm-cov` for host-target test coverage.** The effort is low, the
tool is well-maintained, and it provides meaningful coverage data for the
existing native test suite.

**Do not add Wasm-target coverage** at this time. The experimental workflow,
nightly requirement, and minimal benefit (tests run natively, not in Wasm) do
not justify the complexity.

**Do not add `cargo-tarpaulin`** — it is Linux-only and offers no advantage
over `cargo-llvm-cov` for this project.

### Next steps (if maintainer decides to proceed)

1. Add `cargo-llvm-cov` to CI as shown in §3.1.
2. Configure a coverage threshold in Codecov (e.g., 80% line coverage).
3. Add a `make coverage` target to the Makefile for local runs.
4. Revisit Wasm coverage when `cargo-llvm-cov` stabilises its `wasm-pack`
   subcommand (tracked in
   [cargo-llvm-cov#338](https://github.com/taiki-e/cargo-llvm-cov/pull/338)).
